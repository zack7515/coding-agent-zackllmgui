# 做一個新的 skill

使用者會用一兩句話描述他要的功能。你的工作是把那句話變成一份可用的 `SKILL.md`。

## 步驟

1. **先問清楚，不要急著寫。** 一句話的描述一定不夠，至少要知道：
   - 什麼情況下會用到它？（這決定 `description`，是整份文件最重要的一行）
   - 步驟是什麼？遇到例外怎麼辦？
   - 需要哪些工具？
   用 `ask_user_question` 一次問一件事，不要一口氣丟五個問題。
2. `list_dir skills` 看現有的有哪些，**避免做出重複的**。已經有很像的就說出來，
   問使用者要不要改那一份而不是新增。
3. 想一個 kebab-case 的名字（`run-pytest`、`deploy-staging`）。
4. **寫到 `skills/<名字>/SKILL.md`**（相對於工作區）。
   `write_file` 會自動建資料夾。**資料夾名稱必須跟 `name:` 一模一樣**，
   不然它不會被載入。
5. 驗證：專案裡有 `tests/test_skills.py` 就 `run_tests` 或
   `run_shell python tests/test_skills.py`；沒有的話至少自己再讀一次確認
   `---` 有開有關、`name` 跟資料夾同名、`description` 是一行。
6. 用三行告訴使用者：叫什麼名字、什麼時候會用到、在對話框打 `/` 就叫得出來。

## 放在哪裡才讀得到

兩個地方都會掃，**同名時工作區的蓋掉內建的**：

| 位置 | 用途 | 在 `/` 選單裡 |
|---|---|---|
| `<工作區>/skills/` | 這個專案自己的流程 | 標示「［專案］」 |
| ZackLLMGUI 自己的 `skills/` | 內建的通用範本 | 沒有標示 |

所以你寫的東西一律放**工作區**的 `skills/` —— 那是 `write_file` 唯一碰得到的地方
（路徑限制擋著），也是跟著專案走的地方。想覆蓋內建的某一份，
就用一樣的名字建一個。

**你寫的 skill 裡不要用 `` !`指令` ``。** 那個語法只有在模型改不到的資料夾裡才會
真的執行；寫在工作區裡的載入時只會列出指令、不執行（不然「寫檔案」就變成
「執行指令」，等於自己繞過確認卡）。要用現場狀態就在流程裡寫「先跑 X」。

## 寫 description 的規則

模型只憑這一行決定要不要載入。格式是 **做什麼 ＋ 什麼時候用**，200 字以內、一行。

```
❌ 部署相關的說明
❌ 這個 skill 提供了一套完整的部署流程與最佳實踐
✅ 把 main 部署到 staging 並跑煙霧測試。使用者說要部署、要上 staging 時用。
```

第二個壞例子的問題不是太長，是**沒有一個字在講什麼時候該用它**。

## 寫正文的規則

- 寫**步驟與判斷準則**，不要寫背景介紹 —— 讀到正文時已經決定要用了。
- 每一步講清楚用哪個工具。
- 一定要有「什麼時候不要用這個」那一節。模型很容易把每個 skill 都當成通用解法。
- 上限 8000 字元。超過就代表這應該是兩個 skill。
- `tools:` 只列真的會用到的。列了不存在的工具，驗證測試會直接告訴你。

## 什麼時候不要用這個

使用者只是想問一次性的問題時。skill 是給「會重複好幾次的流程」用的，
一次性的事情直接做就好，不要留下一堆用過一次的 skill 把 context 佔滿。
