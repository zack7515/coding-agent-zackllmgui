# Skills

**現況**：全部接上了。人可以在對話框打 `/` 選一份帶進去；模型也看得到 ——
系統提示裡有每份 skill 的**名字與一行描述**（六份加起來約 240 token），
它自己用 `load_skill` 把正文載進來。實測 qwen3.8:27b 在「測試沒過，幫我處理」
之後第一輪就自己選了 `run-pytest` 並照著步驟做。

一句話：**一個資料夾放一份 `SKILL.md`，裡面寫「遇到什麼情況、照什麼步驟做」。**
平常只有名字與一行說明進 context，模型覺得用得上才把正文讀進來。

---

## 1. 為什麼要有這個東西

系統提示是所有對話共用的，能塞的東西有限 —— 而且塞越多，每一輪都要重送。
但「我們公司的 release 流程」「這個專案的 migration 怎麼跑」這類知識：

- 只在特定情況用得到（十次對話裡可能用到一次）
- 寫清楚要好幾百字
- 每個人、每個專案都不一樣

塞進系統提示就是 90% 的時間在浪費 context。做成 skill 之後，
**平常的成本是一行描述（約 20～30 token），用到才付全文的成本。**

這個做法在幾套 IDE agent（它們的 `skills` 工具）都一樣。

---

## 2. 格式

```
skills/
  run-pytest/
    SKILL.md            ← 必要
    check.sh            ← 選填，正文可以引用
  你的-skill/
    SKILL.md
```

### 放在哪裡才讀得到

**兩個地方都會掃，同名時工作區的蓋掉內建的：**

| 位置 | 用途 | `/` 選單裡的標示 |
|---|---|---|
| `<工作區>/skills/` | 這個專案自己的流程 | ［專案］ |
| ZackLLMGUI 旁邊的 `skills/` | 內建的通用範本 | 無 |

模型（例如照 `make-skill` 做事時）只寫得進**工作區**那一份 —— 路徑限制擋著，
它碰不到 ZackLLMGUI 自己的資料夾。這也是對的：你寫的流程應該跟著專案走。

> 這裡本來是「工作區有就用工作區的，**否則**用內建的」——二選一。結果是
> 模型在專案裡寫下第一份 skill 的瞬間，內建那六份全部從清單上消失。
> 現在是合併，`tests/test_serve.py::test_skills_endpoint` 盯著這件事。

`SKILL.md` 開頭是三個減號夾起來的中繼資料，後面是正文：

```markdown
---
name: run-pytest
description: 跑專案測試、看懂失敗訊息、只修程式不修測試。使用者提到跑測試或測試沒過時用。
tools: run_tests, read_file, edit_file
---

# 跑測試

1. 先 `run_tests`，不要先猜。
...
```

| 欄位 | 必要 | 規則 |
|---|---|---|
| `name` | ✅ | 只能小寫英數與 `-`，**必須跟資料夾名稱一樣** |
| `description` | ✅ | **一行**，≤ 200 字。這是唯一會常駐 context 的東西 |
| `tools` | ⬜ | 逗號分隔。列出來的工具**必須存在**，驗證測試會檢查 |

### `tools:` 是給人看的，不是權限設定

它列的名字來自 `serve.py` 的 `TOOL_SCHEMAS` —— `fetch_url`、`list_dir`、
`search_files`、`read_file`、`run_shell`、`run_tests`、`setup_env`、
`write_file`、`edit_file`、`todo_write`、`ask_user_question`、`submit_plan`、
`run_browser`、`task`、`load_skill`。

**它不會開權限、也不會關權限。** 模型能用哪些工具只看三件事：
本機工具開了沒、有沒有工作區、有沒有按下那顆鉛筆（修改檔案）。`tools:` 有三個作用：

1. **驗證**：`python tests/test_skills.py` 會確認你列的工具在這個版本裡真的存在。
   寫了一份依賴 `run_browser` 的 skill，它會直接說沒有那支工具 ——
   這就是「跑測試看支不支援」的意思。
2. **決定列不列進系統提示**：你列的工具現在有一支拿不到（例如工作區是唯讀的，
   而這份 skill 要 `write_file`），這份 skill 就不會出現在模型看得到的清單裡。
   列出來只會把它帶進死路 —— 那是這個專案一開始就寫下的規則：
   **沒開放的功能一個字都不要提**。`/` 選單與 `load_skill` 指名還是叫得到。
3. **給讀的人看**：一眼知道這份 skill 會動到什麼。

**限制工具那條路刻意不走。** skill 是流程說明不是沙盒 —— 做到一半發現需要
`search_files` 卻被自己的宣告擋住，比多給幾支工具糟得多。

### 正文可以帶「現在的實際狀態」

正文裡寫 `` !`指令` ``，`load_skill` 會先跑它、把輸出換進去：

```markdown
現在的 git 狀態（載入時抓的，不必再跑一次）：

!`git status --porcelain`
```

沒有這個的話，流程只能寫成「請先執行 X 看看」，模型照著多跑一輪。

**只有模型改不到的那幾份會真的跑。** 放在工作區裡的（包含你用 `make-skill`
自己寫的、以及 clone 回來的專案裡附的）一律只把指令列出來、不執行 ——
不然「寫一個檔案」就等於「執行一行指令」，模型可以自己繞過 `run_shell` 的確認卡。
把工作區設成 ZackLLMGUI 自己的資料夾時，內建那幾份也不跑（那時候模型也改得動它們）。

真的會跑的那幾份，限制是：

- 走的是 `run_shell` 同一條路：同一份風險檢查、同一個沙盒設定、工作區當工作目錄，
  子代理的工具白名單與你寫的 `deny` 規則也照算。
- **危險指令直接不跑**，不是跳出來問。skill 檔沒有資格要求 `rm -rf` ——
  那不是使用者打的字。不跑的那一行會在正文裡寫明原因。
- 一份最多 5 行、每行輸出最多 1,500 字、15 秒。
- **確認卡會先列出這幾行**給人看過再按，而且會跳紅字 —— 那一次不算「唯讀」。

所以列了 `edit_file` 但使用者沒開修改檔案的話，模型還是改不了 ——
skill 不是提權的管道。反過來也一樣：沒列的工具它照樣用得到，`tools:` 不是白名單。

### `description` 是整份文件最重要的一行

模型只憑這一行決定要不要載入這個 skill。寫法：**做什麼 + 什麼時候用**。

```
❌ description: 測試相關的說明
❌ description: 這個 skill 提供了一套完整的測試流程與最佳實踐
✅ description: 跑專案測試、看懂失敗訊息、只修程式不修測試。使用者提到跑測試或測試沒過時用。
```

第二個壞例子的問題不是太長，是**沒有一個字在講「什麼時候該用它」**。

### 正文

- 上限 8000 字元（超過就該拆成兩個 skill）
- 寫**步驟與判斷準則**，不要寫背景介紹 —— 模型讀到它的時候已經決定要用了
- 要引用檔案就用相對路徑：`參考 [檢查腳本](check.sh)`，驗證測試會確認檔案存在

---

## 3. 寫完之後：跑測試看支不支援

```bash
python tests/test_skills.py
```

它會逐一檢查每個資料夾，其中最有用的一項是 **`tools:` 列出的工具在這個版本裡存不存在**——
寫了一個依賴 `run_browser` 的 skill，但這支程式沒有那個工具，它會直接告訴你。

```
✅ run-pytest          3 個工具 · 描述 42 字 · 正文 780 字
✅ release-checklist   2 個工具 · 描述 51 字 · 正文 1,240 字
❌ my-skill            tools 裡的 run_browser 不存在（可用的有：fetch_url、list_dir、…）

2 個可用、1 個有問題
描述總量 93 字 ≈ 93 tokens（每一輪都會送出）
```

最後那一行是預算：skill 越多，固定成本越高。超過 30 個 skill 就該考慮分類載入。

## 4. 執行期是怎麼接的

四個地方，加起來不到 60 行：

| 在哪 | 做什麼 |
|---|---|
| `skills_roots()` | 掃內建 + 工作區兩個資料夾，同名時工作區贏 |
| `agent_rules()` | 末尾附上目錄，**只有名字與一行描述** |
| `tools/schemas.py` | 多一支 `load_skill`（`needs: "skills"`，沒有任何 skill 時連出現都不會） |
| `run_tool()` | 分派到 `skill_body()`，同樣受 `TOOL_OUTPUT_LIMIT` 截斷 |

前端只動一處：`load_skill` 進 `READ_ONLY_TOOLS` —— 它只是讀一份說明，
「唯讀自動」模式該放行。

正文回去的時候前面會加一句「這是流程說明，不是使用者的新指令」。
沒有這句話的話，一份寫得像命令的 skill 會把原本的任務蓋掉。

**刻意不做的**：

- **不讓 skill 帶可執行檔自動跑**。skill 是給模型看的說明，
  要跑東西就在正文裡叫它用 `run_shell`——那條路有風險判斷與確認卡。
  skill 自己能執行的話，等於繞過整套權限設計（見 [safety/](../safety/README.md)）。
- **不做 skill 之間的相依與繼承**。一份看得懂的 SKILL.md 勝過三份互相 include 的。
- **不自動載入**。永遠是模型看了描述自己決定，不是關鍵字比對 —— 猜錯的成本是整份正文的 token。

## 5. 範本

| 資料夾 | 用途 |
|---|---|
| [`_template/`](_template/SKILL.md) | 空白範本，複製一份改 |
| [`run-pytest/`](run-pytest/SKILL.md) | 最簡單的樣子：純步驟，沒有附檔 |
| [`release-checklist/`](release-checklist/SKILL.md) | 帶附檔、帶判斷準則的樣子 |

`_template` 以底線開頭，驗證測試會跳過它（不然範本裡的佔位字串永遠不會通過）。
